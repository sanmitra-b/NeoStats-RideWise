# Engineering decisions

**1. Authorisation precedes retrieval.** Firebase verifies identity and trusted custom role claims; a private local mapping binds customer UIDs to IDs. The evaluator can deliberately assume a narrower role. A scoped operational in-memory projection excludes customers/contacts; a separate private profile service rechecks ownership. This prevents a model-generated plan from widening scope. Support contacts require one explicit customer and are masked. Same-process stores simplify the build but are not a process-security boundary.

**2. Plans select typed tools; money is calculated in Python.** The supplied model chooses validated operations/filters, never arbitrary SQL. Parameter binding, scope checks, read-only connections, timeouts and caps protect execution. Payments aggregate at booking grain before joins. Decimal calculations separate successful rental instalments, refunds, deposits and penalties. Entitlement/assessment and recorded payment are compared rather than conflated. This is more predictable than asking the model to calculate financial results.

**3. Evidence is part of the answer contract.** Source pages carry filenames, versions, hashes and extraction methods, including manually reviewed scan transcriptions. The signed v2 refund schedule and tier annexure are retained. Source-hash changes disable calculations pending review. Real streaming worker events make routing inspectable without exposing hidden model reasoning. Each substantive answer includes executed SQL and/or used PDFs; calculations also expose inputs and formulas. Generated citations/numeric tokens are checked and failures fall back to source facts.

**Alternatives rejected.** Docker, a separate frontend build, Postgres/vector services and orchestration frameworks add installation/time costs for five PDFs and a small local database. A raw-SQL agent expands risk and makes authorisation harder. Uploading all customer identities to Firebase/Firestore adds needless PII exposure. Autonomous model instances per worker waste rate limits. Copying SKOPE code would violate fresh-code requirements; its layout and NeoStats visual language are design references only.

**Current limitations.** The query catalogue cannot represent every unseen analytical question; it asks clarification rather than guessing. Lexical page retrieval is weaker than section-level semantic search, and policy-only fallbacks can be verbose. Numeric/citation validation checks provenance, not a mathematical proof of all model claims. Unknown or altered policies require human review. Deposit gateway returns, real-world settlements and holiday calendars are absent. In-memory sessions disappear on restart. Firebase live configuration and event endpoint connectivity require external setup and must be tested independently. Role revocation during a running request is bounded by the next token verification; production requires a stronger revocation strategy. The app does not execute cancellations or refunds.

**One more week.** Add independent claim entailment tests against supplied evidence, a larger read-only typed analytics catalogue, reviewed policy-version ingestion, section/table retrieval and more conversational clarification slots. Put PII behind a separate service and strengthen audit/redaction, session persistence, per-principal quotas and live role-revocation handling. Test the full Firebase evaluator onboarding and performance under event rate limits. Retain the single permitted provider and immutable originals.
